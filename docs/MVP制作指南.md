## 1. 目标与边界

先供主人单人在微信中使用，验证“发消息登记 → 可查询 → 定时提醒 → 确认处理 → 可撤销”。以后接家庭群、飞书等渠道，复用独立库存核心。

本版交付食品和药品的文字录入、日期核实、数量变更、用完/丢弃、撤销、提醒与周汇总。自然语言由现有OpenClaw解析，程序负责校验和持久化。照片录入仍是后续目标，不属于本版已完成功能。

暂缓：语音识别、自动采购、营养/用药建议、多家庭管理界面、自动识别开封后的保存期限。

## 2. 分层

```text
微信私聊 / 后续飞书
    ↓ 渠道适配：验证发送人、原消息 ID、图片、回复路由
AI 解析和交互层：读取内容 → 提议明确命令 → 有歧义追问
    ↓ JSON 命令
库存核心（Python + SQLite）：校验、事务、状态、事件与撤销
    ↓ 到期扫描
待发送队列 → 渠道发送 → 成功后 ack
```

核心不持有微信凭证，不依赖聊天历史存储库存。household 与 actor 由受信任的渠道映射提供，不能让用户消息或模型任意指定。当前为 home / owner。

## 3. 已决定的规则

- 每批物品使用永久 ID，如 #12；清单序号不作为可变位置索引。同名多批必须明确选择。
- 日期来源区分 label（包装）、user（用户明确提供）、estimate（估算）、unknown（未知）。非未知日期必须附依据。
- 药品禁止 estimate；未确认日期保持为空，不因超时自动填一年。
- 食品估算需明确依据并展示“预计处理日”；当前不内置任何生鲜保存天数。
- 有效期日期当天仍显示“今日到期”；过期判定是家庭时区日期大于有效期，不代表适用性判断。
- 生产日期+保质期的换算须确定计量单位和起算口径；月/年不可简单乘以30/365。首版只接受已确认的绝对日期，不让模型自行补全含糊的包装信息。
- 储存方式变化使旧估算失效；不自动推算解冻、开封后的日期。包装日期保留，实际适用性需核实。
- 缺失关键字段可开独立草稿；一小时后按已知信息入库，缺失项仍未知，同时排队知会。迟到补充更新同一条物品。
- 处理区分 consumed 与 discarded；部分处理只扣数量；保留变更事件。撤销只允许本人且物品没有后续修改，防止覆盖更新。
- 无人回复不出库、不删除；过期与是否已处理分开表达。

### 提醒策略

家庭时区 Asia/Shanghai；后台每5分钟扫描，日常提醒从09:30开始发送，周一进行周汇总。22:00至次日08:00不发送。

1. 食品到期前2天、药品前30天进入提前预告阶段，各发送一次。
2. 到期当天起，每日最多一次，成功发送累计3次。
3. 此后只在周一提醒，直到确认用完/丢弃。
4. 未知有效期物品每周一提醒核实。
5. 提前预告不占用到期后的3次额度。发送失败不计数。服务停机后丢弃陈旧的每日提醒，不补发多天消息。
6. 发送器把多项合并成一份清单；成功发送后逐项确认。单纯生成 outbox 不算发送。

具体时间可在渠道调度阶段配置；云端已提供独立 ai-pantry.timer，每5分钟执行tick，发送器控制每日提醒时段。

## 6. 本地运行与验收

Python 3.9+，业务核心无需第三方依赖。

```sh
python3 -m unittest discover -s tests -v
python3 -m pantry.demo
```

示例读取命令（数据库默认 .local/pantry.sqlite3）：

```sh
python3 -m pantry <<'JSON'
{"action":"list"}
JSON
```

写入示例：

```sh
python3 -m pantry <<'JSON'
{"action":"add","request_id":"manual-demo-1","item":{"name":"鲜牛奶","quantity":2,"unit":"盒","expiry":"2026-10-08","date_source":"user","basis":"用户明确提供到期日期"}}
JSON
```

消息ID需固定且唯一，同一消息重试使用相同ID。示例重复执行不会重复入库。

本版最终验收以第4节为准。照片录入单独作为后续阶段验收，不用它阻塞当前文字版试用。

## 7. 已知限制

文字版已部署到用户现有云端 OpenClaw，临期助手文字交互已接入并通过真实OpenClaw工具调用核对；提醒发送参数通过dry-run验证。真实图片识别尚未完成，本轮未重复测试用户已确认的微信互通，也未向微信发送测试提醒。

本地JSON入口只供可信程序调用，不能直接暴露到公网。发送与数据库确认之间仍存在外部系统通用的崩溃窗口：微信成功发送但本地尚未ack时可能重发；当前通过持久化发送尝试，在结果不明确时暂停并要求核对，避免盲目重发；不能宣称端到端恰好一次。

修改日期后按新的日期重新计算提醒；仅改物品名/数量不会重置已经成功的提醒计数。运行时只启动一个发送器，后续多实例需增加队列租约。

## 9. 本次联调发现并修正的问题

1. 模型直接保存未知药品而跳过追问：桥接程序将缺关键字段的add转成draft，用户明确要求先保存未知时才例外。
2. 模型在说明里写了“常温”但没有保存storage：技能明确字段映射，工具返回saved_summary和missing_fields，模型必须核对保存结果。
3. 模型漏传单位导致“一盒”变成“一件”：桥接器要求新增/草稿显式填写品类、数量、单位和温区，回归验证了1盒。

这些修正已部署。真实交互验收采用数据库字段核对，不以模型声称“测试通过”作为唯一依据。
